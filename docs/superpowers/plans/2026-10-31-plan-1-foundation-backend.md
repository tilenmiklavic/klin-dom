# KlinDom Plan 1 — Foundation & Backend Core

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A pnpm monorepo with a Dockerised Postgres + Hono API that implements homes, invites, rooms, tasks, completions, the dashboard rings and stats — fully covered by tests and pushed to GitHub.

**Architecture:** `apps/api` (Hono on Node 22) owns all business rules and talks to Postgres with `pg` and handwritten SQL; schema lives in `db/migrations` (dbmate). Pure domain logic (dates, recurrence, ring math) lives in `packages/shared` so the future app can reuse types and helpers. Auth is a pluggable token verifier: JWKS (Supabase) in production, an HS256 dev issuer for tests and local dev.

**Tech Stack:** pnpm workspaces, TypeScript 5 (strict), Node 22, Hono + `@hono/node-server`, `pg`, `zod`, `luxon`, `jose`, `vitest`, dbmate, Docker Compose, Postgres 16.

**Spec:** `docs/superpowers/specs/2026-10-31-klindom-pwa-design.md`

Later plans (not this one): Plan 2 — `@klindom/ui` + Expo app; Plan 3 — worker/reminders, `daily_rings`, streaks, awards, PWA service worker, deploy.

## Global Constraints

- Node 22 LTS; TypeScript `strict: true`; ESM (`"type": "module"`) everywhere.
- No `@supabase/*` dependency anywhere in `apps/api` or `packages/shared`. Auth provider is reached only through `AUTH_JWKS_URL` / `AUTH_ISSUER` config.
- No Supabase-only features: no RLS policies, no triggers, no `auth.*` schema references. Migrations must run on vanilla Postgres 16.
- All our primary keys are UUIDs generated by Postgres (`gen_random_uuid()`); never reuse the auth provider's IDs as keys.
- All config via env vars; nothing domain-specific hard-coded (`APP_URL` for invite links).
- Dates: a task's `next_due_date` is a `date` in the **home's IANA timezone**; "today" and "this week" (Monday-first) are always computed in the home timezone.
- Recurrence: `next_due_date = localDate(completed_at) + interval`; month arithmetic clamps to month end.
- `completions` is append-only except the undo path (`DELETE /completions/:id`).
- Every endpoint except `/healthz` and `GET /invites/:code` requires a valid bearer token; every home-scoped resource checks membership.
- Error body shape: `{ "error": { "code": string, "message": string } }` with HTTP 400/401/403/404/409.
- Copy in API-generated strings follows the README voice (no "Overdue!", no guilt).

## Review Focus

1. **Timezones & DST** — a home in `Europe/Ljubljana` completing at 23:30 local on the night clocks change must get the local date, not the UTC date. Test in Task 3.
2. **Month-end recurrence** — "every 1 month" done on 31 Jan → due 28 Feb (29 in leap years), not 3 Mar. Test in Task 3.
3. **Two members tick the same task at once** — exactly one `done` completion per task + due_date; the second call returns the existing one with 200. Test in Task 9.
4. **Cross-home access** — a member of home A requesting a task/room/invite of home B gets 404 (not 403, to avoid leaking existence). Test in Task 5 (helper) and re-asserted in Tasks 7–9.
5. **Removed member's leftovers** — after leaving/removal, their assigned tasks become household (`assignee_id = null`) and they can no longer read the home. Test in Task 5.

**Interfaces:**
- Produces:
```ts
type RingTask = { id: string; nextDueDate: IsoDate; intervalCount: number; intervalUnit: 'day'|'week'|'month' };
type RingCompletion = { taskId: string; kind: 'done'|'skip'; completedLocalDate: IsoDate; dueDate: IsoDate };
type Rings = { today: { done: number; total: number }; week: { done: number; total: number }; fresh: { notOverdue: number; total: number; pct: number } };
function computeRings(input: { today: IsoDate; tasks: RingTask[]; completionsThisWeek: RingCompletion[] }): Rings;
```
- Algorithm (spec §7.5, pinned):
  - **today.done** = `done` completions with `completedLocalDate == today` and `dueDate <= today`. **today.total** = today.done + tasks with `nextDueDate <= today`.
  - **week**: `{start,end} = weekBounds(today)`. week.done = `done` completions with `completedLocalDate` in `[start, end]`. Remaining occurrences per task (an overdue task counts once, then recurs from today): `d = nextDueDate; count = 0; if (d <= end) { count += 1; d = addInterval(max(d, today), intervalCount, intervalUnit); while (d <= end) { count += 1; d = addInterval(d, …) } }`. week.total = week.done + Σ count. (A daily task due today on Saturday with nothing done: 2 — Sat + Sun.)
  - **fresh**: total = tasks.length; notOverdue = tasks with `nextDueDate >= today`; pct = total ? round(100·notOverdue/total) : 100.
- `DashboardDto = { rings: Rings; dueToday: TaskDto[] (nextDueDate <= today; overdue first by date, then name); doneToday: (CompletionDto & { taskName, taskIcon, roomNames })[] (done today, dueDate <= today) }`.
- Endpoint: `GET /homes/:id/dashboard?scope=all|mine` (`mine` filters tasks **and** completions to tasks with `assignee_id is null or = me`).
